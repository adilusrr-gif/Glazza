# Ресторан: столы, первый подход и уборка

Модуль связывает текущую занятость мест гостей с задачами сотрудникам. Он использует детектор людей Frigate; отдельная модель лиц, официантов или чистоты стола не устанавливается. Подход и готовность после уборки подтверждает сотрудник. Распознавание этих действий по видео не заявляется.

## Включение

1. Обновите код и пересоберите контейнеры:

   ```bash
   git pull --ff-only
   docker compose --profile nvr --profile ai up -d --build
   ```

   Если анализатор других модулей не используется, достаточно профиля `nvr`. Повторно запускать `scripts/setup.py` не требуется. Таблицы базы добавляются автоматически; существующие камеры, события и пароли сохраняются.

2. В **«Объекты»** создайте объект с профилем **«Ресторан / кафе»** либо включите **«Столы и обслуживание»** у существующего объекта. Назначьте ему камеры зала.
3. Откройте **«Ресторан» → «Сотрудники»**. Добавьте менеджера, официантов и при необходимости сотрудника для уборки. Выдайте каждому персональную ссылку на рабочий экран. Создание или перевыпуск ссылки показывает её один раз; повторный выпуск отзывает предыдущую.
4. Нажмите **«+ Стол»**, выберите камеру, задайте название, ответственных и обведите **места гостей** на кадре. Обводить только столешницу недостаточно: Frigate определяет попадание человека в зону по нижнему центру рамки обнаружения. Не включайте в зону проход официантов.
5. Нажмите **«Применить настройки»**. В конфигурацию Frigate добавятся отдельные ресторанные зоны и подключение к внутреннему MQTT. NVR перезапустится. До получения актуального состояния настроенной зоны стол остаётся серым.
6. Для пустого подготовленного стола подтвердите **«Убрано»**. Он станет зелёным. Новый стол не считается автоматически чистым только потому, что его ещё никто не занимал.

Ресторанные зоны не являются запретными и не создают тревоги проникновения. Они управляются в разделе «Ресторан» отдельно от охранных зон камеры. При изменении геометрии создаётся новое имя зоны: старые данные NVR не могут подтвердить новую разметку до её применения.

Персональную ссылку открывают по доступному сотруднику адресу Glazza. `localhost` на телефоне означает сам телефон; используйте настроенный адрес сервера. Для доступа из внешней сети используйте существующее HTTPS-развёртывание, описанное в [эксплуатации](OPERATIONS.md). Брокер MQTT наружу не публикуется.

## Состояния и таймеры

| Отображение | Значение | Переход |
|---|---|---|
| Зелёный | Пустой стол, подготовка подтверждена | Устойчивая посадка запускает визит |
| Красный, «Ожидают официанта» | Есть новый визит, первый подход не подтверждён | «Подошёл» закрывает ожидание |
| Красный, «Обслуживаются» | Подход подтверждён, гости остаются за столом | Устойчивое отсутствие гостей запускает уборку |
| Жёлтый | Требуется проверить уход и подготовить стол | «Убрано» при актуальном пустом столе возвращает зелёный |
| Серый | Нет достоверного текущего наблюдения либо идёт подтверждение посадки | Нужны актуальные данные камеры и зоны |

Настройки каждого стола:

- **Ожидание первого подхода:** 120 секунд по умолчанию, диапазон 30–1800.
- **Подтверждение посадки:** 5 секунд, диапазон 1–60. Таймер первого подхода отсчитывается от начала подтверждённого присутствия, а не добавляет к нормативу задержку подтверждения.
- **Подтверждение отсутствия гостей:** 60 секунд, диапазон 10–600. Короткое пропадание из зоны не завершает визит.

Эти интервалы — стартовые настройки для пилота, а не измеренная точность распознавания. Камера видит присутствие людей в заданной зоне. Она не знает, является ли человек гостем, и не может по одному отсутствию доказать окончательный уход.

**«Гости отошли»** сохраняет текущий визит и блокирует автоматический переход на уборку. **«Вернулись»** снимает эту отметку. Подходящий человек, неподвижно сидящий гость и отсутствие всех гостей проверяются по состояниям зон, а не по движению пикселей.

## Кому поступают сигналы

1. Подтверждённая посадка → назначенному официанту.
2. Подход не подтверждён к дедлайну → активным менеджерам того же объекта.
3. Гости отсутствуют дольше заданного интервала → назначенному сотруднику уборки; если его нет — официанту.

Если ответственный отсутствует или отключён, задача направляется менеджерам. Если нет менеджера, она остаётся в панели администратора с диагностикой отсутствующего назначения. При назначении нового менеджера незакрытые задачи получают актуального адресата.

**«Принято» подтверждает получение уведомления.** Оно не заменяет **«Подошёл»**, не останавливает таймер первого подхода и не отмечает уборку. Каждое действие связано с идентификатором текущего визита. Старую задачу нельзя применить к новой посадке.

Официант видит назначенные ему столы и адресованные ему уведомления. Сотрудник уборки видит свои столы и может подтвердить подготовку. Менеджер видит столы своего объекта. Эти экраны не имеют доступа к настройкам камер, реестру допуска или административной панели.

Персональная ссылка является доступом к рабочему экрану: выдавайте её конкретному сотруднику. В базе хранится хеш ключа. Браузер удаляет ключ из адресной строки, использует память сессии вкладки и передаёт его в заголовке авторизации. Отключение сотрудника или перевыпуск ссылки отзывает доступ.

### Экран сотрудника и звук

Экран обновляется каждые две секунды. Кнопка **«Включить звук»** разрешает звуковой сигнал и, где поддерживается, вибрацию. При пропадании соединения данные помечаются устаревшими и действия блокируются.

Открытая вкладка нужна для визуального/звукового сигнала браузера. Это не Web Push: доставка при закрытой вкладке или заблокированном телефоне не гарантируется. Серверные таймеры продолжают работать независимо от вкладки.

### Telegram, по желанию

Для внешней доставки добавьте в существующий `.env`:

```dotenv
GLAZZA_TELEGRAM_BOT_TOKEN=ваш_токен_бота
```

В карточке сотрудника укажите числовой `chat ID` и пересоздайте API-контейнер:

```bash
docker compose up -d --build glazza
```

У бота должен быть доступ к выбранному чату; для личного чата сотрудник предварительно открывает бота и начинает диалог. Отправляется текст задачи: стол, событие и время ожидания. Видео и фотографии в Telegram не отправляются. Для этого канала требуется интернет.

Задачи хранятся в очереди. Неудачные доставки повторяются с увеличением интервала; после восьми попыток отображается ошибка, сама задача остаётся в панели. Нажатие «Принято» или закрытие задачи отменяет ещё не отправленные сообщения. При сетевой неопределённости после отправки повторное сообщение возможно: Telegram `sendMessage` не предоставляет гарантии единственной доставки при повторе запроса.

## Текущие данные и восстановление

Compose включает Mosquitto 2.0.22 во внутренней сети, без опубликованного порта 1883. В API по умолчанию используется хост `mqtt`. При запуске API вне Compose задайте `GLAZZA_MQTT_HOST`, при необходимости `GLAZZA_MQTT_PORT` и `GLAZZA_MQTT_PREFIX`. Подключение рассчитано на доверенный локальный брокер.

Интеграция проверена по протоколу Frigate 0.18.2:

- `frigate/<zone>/person` — все люди, включая неподвижных; `/active` не используется;
- `frigate/available` — доступность NVR;
- состояния включения камеры, детекции и конкретной зоны;
- `frigate/onConnect` → `frigate/camera_activity` — полный текущий снимок после переподключения и каждые пять секунд, поскольку счётчики зон публикуются только при изменениях;
- измеренный FPS камеры и свежесть статистики из существующего мониторинга Glazza.

Источники протокола: [MQTT](https://docs.frigate.video/integrations/mqtt/), [CameraActivityManager 0.18.2](https://github.com/blakeblackshear/frigate/blob/v0.18.2/frigate/camera/activity_manager.py), [Dispatcher 0.18.2](https://github.com/blakeblackshear/frigate/blob/v0.18.2/frigate/comms/dispatcher.py).

Отключение камеры, детекции, зоны или брокера переводит наблюдение в неизвестное. Оно не означает уход гостей. После перезапуска сервера сохранённый визит и дедлайн остаются, а присутствие людей подтверждается заново. Просроченный неподтверждённый подход всё равно виден менеджеру; при отсутствии данных сообщение прямо указывает невозможность текущей проверки камерой.

SQLite хранит настройки, сотрудников, визиты, уведомления и аудит. Завершённая история удаляется по `GLAZZA_RETENTION_DAYS`; текущие визиты и незакрытые задачи сохраняются. Поддерживается один экземпляр API, как и в остальных модулях Glazza.

## Приёмка на реальном объекте

Начните с одной камеры и нескольких хорошо видимых столов. Проверьте дневной и вечерний свет, неподвижных гостей, проход официанта мимо, выход одного человека из группы, временный выход всех гостей, уборку, отключение камеры и перезапуск API.

Измеряйте пропущенные посадки, ложные вызовы, ошибочное завершение визита и время доставки сигнала. Программные тесты не оценивают точность детектора на ваших камерах. Закрытые креслами/колоннами места и неудобный ракурс могут потребовать переноса камеры или изменения разметки.

Проверки кода:

```bash
python -m pytest -q tests/test_restaurant.py tests/test_restaurant_feed.py
node --check app/static/restaurant.js
node --check app/static/staff.js
PYTHONPATH=. python tests/browser_restaurant.py
```
