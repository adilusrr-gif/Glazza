# Как измерить качество сигналов о возможной краже в магазине

Владелец магазина получает два показателя для решения о пилоте: сколько размеченных эпизодов система подняла на проверку и сколько лишних тревог пришлось на час видео с одной камеры. Для их расчёта Glazza может повторно обработать локальные записи тем же маршрутом анализатора, который использует рабочая система. Оператор сверяет результат с разметкой, сделанной до запуска модели.

## Основной режим магазина: маршрут без весов модели

1. До включения отчёта зафиксируйте магазин, камеры и границы целых контрольных периодов. Сохраните полную запись за эти часы, интервалы потери видеопотока или архива, время недоступности Frigate и правила. Сделайте штатный снимок базы командой `python scripts/backup.py` до очистки истории. Для расчёта нужен только `glazza.db` из снимка. Экран журнала ограничивает количество карточек на страницу.
2. Сотрудник, который ещё не видел карточки, просматривает весь доступный период. Для проверки правила он отмечает видимый проход от полки к выходу в обход кассовой зоны. Каждому эпизоду присваивает ID и отмечает интервал от ухода от полки до достижения выхода. Уход без товара тоже может соответствовать маршруту. Итоги по возможным потерям ведите отдельно.
3. Создайте файл периодов. `start` и `end` — Unix-время в секундах. Интервалы `span` и `gaps` отсчитываются от `start`. Для неразмеченного периода ставьте `reference_complete: false`. В `gaps` включите интервалы, где независимая проверка по архиву или сравнение с журналом невозможны. Если система была выключена, но независимая запись и полный журнал доступны, оставьте время в расчёте: пропущенный системой эпизод должен попасть в отчёт. Укажите границы без разрезания проверяемых маршрутов.

```json
{"periods":[{"site_id":"shop-1","camera":"aisle-2","start":1800000000,"end":1800003600,
  "gaps":[[900,960]],"events":[{"id":"R1","span":[210,227]}],
  "reference_complete":true,"reviews":{}}]}
```

4. Выгрузите реальные карточки за указанные периоды. Команда читает снимок базы в режиме только для чтения и возвращает идентификаторы, интервалы и состояния карточек. В выборку попадает источник `retail_route` по указанной камере и магазину. Карточка относится к периоду по времени достижения выхода, правая граница периода исключается.

```bash
python -m scripts.evaluate_routes backups/<снимок>/glazza.db data/theft-eval/periods.json > data/theft-eval/routes.json
```

5. Второй сотрудник сверяет каждую карточку по видео с независимой разметкой, особенно если рядом проходят несколько людей. В `reviews` внесите, например, `{"фактический_id_карточки":{"reference_id":"R1","operator_seconds":23}}`. Для лишнего сигнала или второй карточки по тому же проходу укажите `reference_id: null`. У необработанной карточки пока нет записи в `reviews`. `operator_seconds` — измеренное активное время работы обычного оператора с карточкой. Если замера не было, пропустите поле.
6. Запустите команду ещё раз. Код 0 означает завершённую сверку наблюдаемого времени, код 1 — неполную сверку или отсутствие наблюдаемого времени, код 2 — ошибку данных. Автоматической приёмки магазина команда не выполняет.

| Вопрос владельца магазина | Что смотреть в полевом отчёте |
|---|---|
| Какую часть смены проверили? | `observable_camera_hours / planned_camera_hours`, причины каждого разрыва и лежащие в нём эпизоды `unobservable_reference_ids` |
| Какие проходы пропущены? | `missed_reference_ids` по каждому периоду и `recall` по размеченным проходам |
| Сколько лишней работы? | `false_alerts_per_observable_camera_hour`, число ложных карточек, измеренные `measured_operator_seconds` и количество замеров `timed_cards` |
| Сколько карточек передали на разбор? | `escalated_cards` — текущее количество карточек со статусом «Отмечено для разбора». Для бизнес-результата отдельно сверьте чек, товар и заключение ответственного сотрудника. Отдельно укажите случаи, по которым данные об оплате недоступны. |

При неполной разметке или открытой сверке отчёт возвращает `null` для precision, recall и частоты ложных тревог. Карточки за пределами наблюдаемого видео перечислены отдельно. Учитывайте нагрузку по фактически измеренному времени, а результат проверки маршрута не подставляйте в сумму предотвращённых потерь.

## Дополнительный режим VadCLIP: подготовка записей

1. Выберите камеры и целые отрезки смены заранее, сохранив обычные часы, очереди, периоды без покупателей и разные условия освещения. Пометьте такие записи как `continuous`. Если отбирать клипы по готовым тревогам, пропущенные системой события исчезнут из расчёта.
2. Разметьте начало и конец видимых эпизодов, для которых оператор действительно должен открыть карточку. В спорных случаях согласуйте разметку со вторым сотрудником. Основание для вывода о неоплате проверяется отдельно по обстоятельствам и кассе.
3. Добавьте подборку сложных примеров как `curated`. Полезны возврат товара на полку, телефон из кармана, собственная сумка, перекрытие другим посетителем. Постановочные примеры относите к этой же группе. Их результаты выводятся отдельно.
4. Делите исходные записи на фрагменты до 120 секунд. У каждого размеченного эпизода должны помещаться в один файл и начало, и конец. Укажите длительности по медиаданным, не округляя до целых секунд. Для сплошной записи фрагменты покрывают исходный материал целиком, без пропусков и наложений. Если источник оборвался, заведите отдельные записи до и после обрыва и отдельно учтите простой камеры.
5. Отведите разные исходные записи и смены для настройки (`calibration`) и финальной оценки (`test`). При переносе на новый магазин добавьте в финальную оценку его камеры. Для повторных кодировок одного исходника сохраняйте его идентификатор. Скрипт проверяет повтор идентификатора «камера + запись» и одинаковые байты клипа во всём манифесте. Переименование и повторное кодирование исходника одновременно требуют ручной проверки.
6. До открытия финальной выборки согласуйте с магазином минимальный объём непрерывного обычного видео, число размеченных эпизодов и допустимую нагрузку оператора. Сохраните отдельно файлы настройки и результаты. Выбор нового порога после финальной проверки требует новой отложенной выборки.

Пример `manifest.json` для двух файлов одной камеры. Имена и интервалы иллюстрируют формат. Все временные величины даны в секундах. `start_seconds` относится к началу исходной записи, а `events` — к началу конкретного файла. Пустой список означает, что разметчик просмотрел фрагмент и не нашёл целевого эпизода.

```json
{
  "recordings": [{
    "camera": "aisle-2",
    "recording": "evening-shift-excerpt-001",
    "split": "test",
    "sample": "continuous",
    "duration_seconds": 120.0,
    "clips": [
      {"file": "aisle2-001.mp4", "start_seconds": 0.0, "duration_seconds": 60.0, "events": []},
      {"file": "aisle2-002.mp4", "start_seconds": 60.0, "duration_seconds": 60.0, "events": [[12.0, 17.5]]}
    ]
  }]
}
```

## Запуск

Подготовьте модель по инструкции в [MODELS.md](MODELS.md). Поместите манифест и видео в локальную директорию, например `data/theft-eval/`. В среде с зависимостями анализатора, включая PyTorch и FFmpeg, выполните из корня репозитория:

```bash
python -m scripts.evaluate_theft data/theft-eval/manifest.json --models ./models > data/theft-eval/report.json
```

Для сервера с собранным образом анализатора тот же тест можно запустить отдельно от рабочих очередей:

```bash
docker compose --profile ai run --rm --no-deps \
  -v "$PWD/scripts:/opt/glazza/scripts:ro" \
  -v "$PWD/data/theft-eval:/eval:ro" \
  analyzer python -m scripts.evaluate_theft /eval/manifest.json --models /models \
  > data/theft-eval/report.json
```

Параметр `--split calibration` выбирает настройку, по умолчанию выбирается `test`. Для первого исследования достаточно отчёта без целевых значений. Для проверки согласованных целей передайте `--targets путь/targets.json`. Пример формата с **иллюстративными** значениями:

```json
{
  "min_normal_camera_hours": 48,
  "min_events": 20,
  "min_precision": 0.70,
  "min_recall": 0.80,
  "max_false_alerts_per_camera_hour": 0.10
}
```

В примере допускается в среднем одна лишняя тревога на 10 камера-часов. На 8 камерах, работающих по 12 часов, это около 10 лишних проверок за смену. Минимальный объём обычного видео включает только целиком отрицательные фрагменты непрерывной записи. Время обработки файлов, ожидание уведомления, простой камеры и длительность смены — разные величины.

## Чтение результата

| Поле | Как его читать |
|---|---|
| `continuous.tp / fp / fn` | Совпавшие сигналы, лишние сигналы и пропущенные размеченные эпизоды в проверенных непрерывных записях |
| `precision` | Доля сигналов, совпавших с разметкой, TP / (TP + FP) |
| `recall` | Доля найденных размеченных эпизодов, TP / (TP + FN) |
| `false_alerts_per_camera_hour` | Все лишние сигналы на сплошных записях, делённые на сумму длительностей проверенных клипов в часах |
| `checked_clips / clips` | Покрытие проверкой. В `clips` верхнего уровня указана причина сбоя по каждому файлу |
| `curated` | Результаты отдельно отобранных примеров. Доля ложных тревог в смену по таким данным не оценивается |
| `predicted / expected` | Интервалы по каждому файлу, которые можно перепроверить вручную |
| `processing_seconds` | Время отдельного вызова офлайн-анализатора с декодированием |

Один сигнал может совпасть с одним размеченным эпизодом. Критерий совпадения — отношение длительности пересечения к длительности объединения интервалов, `--min-iou`, по умолчанию 0.10. Выберите это значение до теста. Повторный сигнал по уже сопоставленному эпизоду считается лишним. Сигнал в другой части положительного ролика также считается лишним. `null` означает, что у метрики нет знаменателя.

Код завершения 0 при статусе `measured` означает, что расчёт выполнен. `offline_targets_met` означает, что цели выполнены на непрерывных отложенных записях. Код 1 соответствует `incomplete` (есть непроверенные клипы), `insufficient_evidence` (нет нужного объёма отложенных данных) или `targets_missed`. Код 2 означает ошибку входных параметров. Отсутствующие веса и запись, по которой анализатор не смог проверить кражу, не дают отрицательного примера. В отчёте остаются хеши весов, манифеста и файлов, порог и число последовательных образцов.

Наконец проведите прогон на подключённой камере. Для нескольких отмеченных эпизодов сопоставьте видео, момент появления карточки, доступность фрагмента и решение оператора. Отдельно измерьте задержку от начала эпизода до карточки и долю времени, потерянного при отключении камеры или очереди. Офлайн-отчёт покрывает распознавание на переданных файлах. Он не измеряет отбор видео самим Frigate, задержку доставки, нагрузку на многокамерном сервере или перенос качества на следующий магазин.
